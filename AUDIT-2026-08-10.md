# Audit du dépôt GeoTrack Team

Date : 10 août 2026  
Portée : archive `GeoTrack-Team-main.zip` fournie par l'équipe

## Verdict

Le dépôt contient une base technique sérieuse, mais l'archive initiale n'était pas prête pour une remise. Le défaut principal était la troncature de 21 documents Markdown au milieu de leur premier bloc de code. L'arborescence contenait aussi plusieurs répétitions de dossiers, deux extensions d'image incorrectes et des livrables annoncés mais vides.

La version corrigée répare les défauts sûrs et rend le dépôt lisible et vérifiable. Elle ne remplace toutefois pas la validation finale avec Jira, les sources Figma, les résultats de tests système et les exigences exactes du professeur.

## Contrôles réalisés

- intégrité de l'archive ZIP ;
- inventaire des fichiers et dossiers ;
- détection des chemins imbriqués ou dupliqués ;
- vérification des blocs Markdown et des liens locaux ;
- validation syntaxique du JSON Schema ;
- compilation et exécution du simulateur Python ;
- examen visuel des trois images ;
- comparaison des champs de télémétrie entre le schéma, le simulateur et la documentation ;
- inventaire des User Stories représentées dans les noms de fichiers.

## Corrections appliquées

### Structure

- Déplacement des trois documents US-08 depuis `calculations/docs/donnees/...` vers `docs/donnees/`.
- Déplacement des règles US-11 depuis `diagrams/docs/analyse/` vers `docs/analyse/`.
- Déplacement du README de sécurité depuis `docs/donnees/docs/securite/` vers `docs/securite/`.
- Suppression des niveaux de dossiers devenus vides.
- Renommage de `US-04-interface-principale.png.png` en `US-04-interface-principale.png`.
- Renommage de `US-10-tableau-de-bord-analytique.png.png` en `US-10-tableau-de-bord-analytique.png`.
- Ajout d'un `.gitignore` pour les fichiers temporaires courants.

### Documentation

- Fermeture et complément des 21 documents tronqués.
- Alignement des champs US-08 sur le contrat JSON : `speed_kmh`, `direction_deg`, `status` et `diagnostic`.
- Ajout de critères de validation, limites, mécanismes d'idempotence, règles d'ordre, gestion des erreurs et compromis dans les documents concernés.
- Réécriture du README racine avec objectifs, dimensionnement, arborescence et état des US.
- Ajout d'index dans les README de dossiers.
- Ajout d'un registre de 12 risques dans `docs/risques/registre-risques.md`.
- Ajout d'une matrice initiale de 15 scénarios dans `docs/tests/strategie-validation.md`.

### Simulation

- Ajout d'arguments de ligne de commande : nombre de véhicules, intervalle, cycles, taille d'échantillon et graine aléatoire.
- Exécution finie par défaut pour rendre le test reproductible.
- Conservation d'un mode continu avec `--cycles 0`.
- Horodatage UTC normalisé avec le suffixe `Z`.
- Documentation des commandes d'exécution.

## Points cohérents

- Le calcul nominal de 10 000 / 5 = 2 000 messages par seconde est exact.
- Le calcul de 126 144 000 000 messages sur deux ans est exact avec 365 jours par année.
- Le calcul brut de 37 843 200 000 000 octets, soit 37,84 To décimaux, est exact avec l'hypothèse de 300 octets.
- Le schéma JSON, le simulateur et la documentation utilisent maintenant les mêmes champs principaux.
- Le diagramme US-11 correspond au scénario principal décrit et montre un cas alternatif d'erreur.

## Points encore bloquants avant la remise

### 1. Correspondance avec Jira non vérifiée

Le ZIP ne contient ni export Jira ni métadonnées Git. Il est donc impossible de confirmer dans cet audit :

- le statut réel de chaque ticket ;
- les critères d'acceptation approuvés ;
- les responsables et Story points ;
- les branches, commits et Pull Requests ;
- l'équilibre des contributions.

Action : comparer le tableau Jira et l'historique GitHub à la matrice des fichiers avant la remise.

### 2. US-05 et US-12 absentes

Aucun fichier de l'archive ne porte les préfixes US-05 ou US-12. Cela peut être normal si elles ont été retirées ou réaffectées, mais le dépôt seul ne permet pas de le prouver.

Action : vérifier dans Jira si ces US sont annulées, hors périmètre, dupliquées ou simplement manquantes. Ne pas créer de faux livrable sans vérifier.

### 3. Diagrammes insuffisants dans l'archive

Le dossier `diagrams/` contient seulement le diagramme de séquence US-11. Son README annonce aussi un diagramme de cas d'utilisation et un diagramme d'architecture globale, mais ils ne sont pas présents.

Action : ajouter les exports et, si possible, les fichiers sources modifiables demandés par le cours.

### 4. Rapport final non assemblé

Le dossier `rapport/` contient une section de sécurité, mais pas le rapport final complet. Les contenus techniques sont dispersés dans le dépôt.

Action : assembler le rapport selon le gabarit et les critères exacts du professeur, sans copier intégralement chaque document technique.

### 5. Maquette Figma à corriger manuellement

L'export du tableau de bord présente des problèmes visibles : le texte « Toutes les zones » est coupé et plusieurs éléments de la section « Alertes récentes » se chevauchent ou se replient mal. Le lien vers le fichier Figma modifiable est absent.

Action : corriger les contraintes de largeur et d'alignement dans Figma, réexporter l'image, puis ajouter le lien du prototype si demandé.

### 6. Tests système non exécutés

La stratégie de tests est maintenant documentée, mais la majorité des scénarios restent à exécuter. Il n'existe pas encore de preuve de charge, de panne, de restauration, de RBAC ou de performance du navigateur.

Action : exécuter en priorité T-04, T-05, T-06, T-07, T-11, T-13 et T-14, puis joindre les preuves.

## Risques de contenu à faire valider par l'équipe

- Le facteur de pointe de 2 et la cible de 4 000 messages par seconde sont des hypothèses de test proposées, pas des exigences confirmées.
- La cible de latence de traitement p95 inférieure ou égale à 2 secondes est une proposition d'architecture.
- Les périodes Hot 0-30 jours, Warm 31-180 jours et Cold 181 jours-2 ans sont configurables.
- Les objectifs RPO de 5 minutes et RTO de 30 minutes doivent être validés par le métier.
- Le seuil séparant activité et arrêt d'un véhicule doit être confirmé afin de tenir compte du bruit GPS.

## Procédure recommandée pour intégrer les corrections

1. Conserver une copie de l'archive d'origine.
2. Décompresser la version corrigée dans un dossier distinct.
3. Créer une branche Git dédiée, par exemple `fix/audit-2026-08-10`.
4. Copier les fichiers corrigés dans le clone Git existant sans supprimer le dossier caché `.git`.
5. Examiner `git status` et `git diff`.
6. Valider avec l'équipe les hypothèses signalées ci-dessus.
7. Créer un commit, puis une Pull Request vers `main`.
8. Fusionner seulement après la revue d'un autre membre.

## Conclusion

La version corrigée constitue une base propre pour la revue d'équipe. Les défauts techniques internes de l'archive ont été corrigés, mais la remise ne doit pas être déclarée complète avant la vérification Jira/GitHub, l'ajout des diagrammes manquants, la correction Figma, l'assemblage du rapport et l'exécution des tests prioritaires.
